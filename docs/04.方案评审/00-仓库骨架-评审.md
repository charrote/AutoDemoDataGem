# 00 · 仓库骨架 — 评审

> 评审对象：`docs/03.实现/00-仓库骨架.md`（对应《02.技术实现方案.md》§9 任务 0.0）
> 评审人：Agent-395-Hermes ｜ 日期：2026-09-21
> 评审维度：合理性 / 实现与运营风险 / 后续成本（统一评审报告见 [README.md](./README.md)）

## 结论

**⚠️ 有条件通过** — 骨架设计本身合理，但有一个与 11/43 互相矛盾的关键语义（VAULT_KEY）和一处依赖缺口（PG 驱动）必须在开工前定掉。

## 1. 合理性

- monorepo 目录（api/ web/ connectors/ docker/）与「一个系统 = 一个连接器包」的插件形态匹配，目录边界清晰，扩展点正确。
- 「web/api 启动不依赖 DB」是首启向导（43）的前置条件，依赖方向正确。
- 内置 MySQL 放进 `builtin-db` profile 按需拉起，对单机部署是合理的妥协。

## 2. 实现风险

- **VAULT_KEY 语义矛盾（跨卡 R1）**：11 要求「无 `VAULT_KEY` 启动即失败」，而本卡验收要求 `docker compose up -d` 起 api 且 `/api/health` 返回 200（此时 .env 还是占位）。两者不能同时满足，fail-fast 的边界必须明确（建议：进程级 fail-fast + 提供 `make gen-env` 生成 .env，把「先配 .env 再 compose up」写进部署前提）。
- **依赖列表缺 PG 驱动**：本卡依赖清单是 asyncmy(aiomysql) + aiosqlite，但 12 的验收标准包含 Postgres 适配，缺 `asyncpg`。
- Vue 骨架 + node 构建层：Dockerfile 未提及 `.dockerignore`，构建会慢且镜像大（工程细节，低风险）。

## 3. 运营风险

- compose 示例中内置 MySQL 默认会 publish 3306 到宿主机；在共享宿主（nat.ywapi.com）上应改为仅 compose 网络内可达，避免与 MES-v24 的 3306 冲突。
- 端口 8860/8861 与 MES-v24 的冲突需要部署前确认（44 同机问题，联动）。

## 4. 后续成本

低。一次性骨架，无持续维护。

## 5. 整改建议

| # | 建议 | 优先级 |
|---|------|--------|
| 1 | 明确 VAULT_KEY fail-fast 边界 + 提供 `make gen-env`（openssl rand -hex 32）生成 .env，与 11/43 统一口径 | 高 |
| 2 | 依赖列表补 `asyncpg`，与 12 的 PG 验收对齐 | 高 |
| 3 | 内置 MySQL 不 publish 3306（仅 compose 内网） | 中 |
| 4 | 锁定 Python 3.12 基础镜像版本；补 .dockerignore | 低 |
