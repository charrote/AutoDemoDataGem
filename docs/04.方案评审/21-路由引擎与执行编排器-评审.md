> 评审对象：`docs/03.实现/21-路由引擎与执行编排器.md`（对应《02.技术实现方案.md》§9 任务 2.1）
> 评审人：Agent-395-Hermes ｜ 日期：2026-09-21
> 评审维度：合理性 / 实现与运营风险 / 后续成本（统一评审报告见 [README.md](./README.md)）

## 结论

**⚠️ 有条件通过** — 状态机 + 分阶段 + 分块/重试/限流是正确设计；两处关键细节必须补：幂等检查的查询代价（R5）与「API 返回 ID 不可得」的 manifest 退化路径。

## 1. 合理性

- 路由引擎只做标签分发，判断「哪条走哪路」是连接器专家知识（D2 决策），引擎薄、连接器厚，职责划分正确。
- Run 状态机（pending → running(phase…) → done|failed|cancelled）+ 4 阶段顺序执行，覆盖 MVP 需求。
- Dry-Run 先行 + manifest 幂等 + 退避重试 + 限流 + 进度推送，鲁棒性设计完整，与方案 §2.6 一致。

## 2. 实现风险

- **幂等检查的查询代价（R5）**：「写前不重复」需要查 manifest（本 run 已写哪些 ID）。若每批查一次全量 manifest 到内存再过滤，大 run（数万行）会拖慢。建议：manifest 按 `(run_id, table)` 分片查询，只取当前表/当前阶段的已写 ID 集合；或者「重试只从失败点续跑」（阶段级断点，而非行级去重）——后者更简单且覆盖 90% 场景。
- **API 返回 ID 不可得的退化路径**：方案 §2.9 说「DB 与 API 返回 ID 都记」，但很多写接口不返回 ID（返回 200 + bool 或 204）。manifest 对 API 条目的记录格式必须定义：能拿 ID 记 ID，拿不到记「接口 + 请求体指纹」（sha256 of canonical payload），重置时按指纹反查（或标记「无法精确重置，需人工确认」）。不定义这个退化，41 的重置会在 API 通道上失效。
- **阶段间依赖**：阶段 3（流程/状态 API）依赖阶段 2 的 DB 数据（引用主 ID）。若阶段 2 部分失败（重试后），阶段 3 引用的 ID 是否有效？建议：阶段完成才推进下一阶段，阶段内失败 = Run 失败 + 精确到批（不进入下一阶段）。
- **限流粒度**：对目标系统 API 限速，限流器是全局（所有 run 共享）还是 per-run？MVP 单机单用户，per-run 即可，但要避免「多个 run 并发跑」的未定义行为（建议：同一 system 同时只允许一个 run，排队或拒绝）。

## 3. 运营风险

- **进程内异步任务（D1）的崩溃恢复**：FastAPI 后台任务在进程重启后丢失。MVP 单机可接受（重启 = 该 run 失败，用户重跑），但要：run 状态落库（runs 表已有），重启后把 `running` 状态的 run 标记为 `failed`（「进程重启中断」），不留下僵尸 running。
- **进度推送**：轮询 vs WebSocket 未定。建议 MVP 用轮询（简单、无状态），WebSocket 作为阶段 2 增强；避免 MVP 引入 WS 的复杂度。
- 失败定位「哪条接口哪条数据」：日志要带 run_id + phase + 表/接口 + 行索引/ID，格式统一，方便用户截图反馈。

## 4. 后续成本

- 编排器是核心，一次投入。
- 若未来上量（多租户并发 run），D1 的进程内任务会撞墙，需迁 Celery（方案已预留接口）——这是已知的阶段 2/3 成本，MVP 不承担。
- manifest 退化路径（指纹）若不做，41 重置在 API 通道的实现成本会翻倍（要反向工程「哪些是工具写的」）。

## 5. 整改建议

| # | 建议 | 优先级 |
|---|------|--------|
| 1 | 补 manifest 退化路径：API 无 ID 时记接口+payload 指纹，定义重置语义 | 高 |
| 2 | 幂等策略明确：阶段级断点续跑（推荐）或 manifest 分片查询 | 中 |
| 3 | 同 system 同时只允许一个 run（拒绝或排队） | 中 |
| 4 | 进度推送 MVP 用轮询；进程重启后把 running→failed | 低 |
