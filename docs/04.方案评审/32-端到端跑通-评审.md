# 32 · 端到端跑通 — 评审

> 评审对象：`docs/03.实现/32-端到端跑通.md`（对应《02.技术实现方案.md》§9 任务 3.2）
> 评审人：Agent-395-Hermes ｜ 日期：2026-09-21

## 结论

**⚠️ 有条件通过** — 这是 MVP 成败点，设计方向正确；但验收标准「看板活」需要量化，否则「看起来活」无法客观判定。

## 1. 合理性

- 完整运行链路（选场景→调参→Dry-Run→确认→运行→监控）是产品承诺的闭环，本卡是 MVP 的核心证明。
- manifest 记录（DB + API 返回 ID 都记）+ 进度推送（阶段完成度 + 实时日志流），鲁棒性与可观测性都有。
- 「双通道都证明：DB 写扁平/历史 + API 推进流程态 + 触发 SPC/KPI 重算」——这是产品「和灌数脚本的区别」的最终验证，方向正确。

## 2. 实现风险

- **「看板活」的验收标准无法量化**：「时间新鲜 + 有关系 + 分布合理 + 有异常」4 条标准在 31 的 Dry-Run 里是「预览数据符合」，但 32 是「灌完看板活」——**如何判定「活」**？建议：定义客观检查项：
  - 时间新鲜：最近 24h 内有 ≥ N 条记录（查 DB）；
  - 有关系：从表外键 100% 指向存在的主表记录（查 DB）；
  - 分布合理：状态比例在配方声明的 ±5% 内（查 DB 聚合）；
  - 有异常：不良率/异常条数 ≥ 配方 anomaly_rate 的 50%（查 DB 聚合）。
  这 4 条可以写成自动化检查脚本（Python），作为本卡的验收工具，而不是「人眼看看板」。
- **依赖 30 的 Q1/Q2 全部落地**：本卡是 30 的下游，Q1/Q2 未核实则本卡无法开工。建议在 README 里程碑里明确：M3（30→32）的开工门槛 = Q1 写 API 实测通过 + Q2 schema 起库验证通过。
- **API 通道的写操作对真实 QM-AI 的污染**：本卡的「在 QM-AI 实灌一次」是对生产环境的写操作。运营风险同 30（专用实例 / 演示前重置 SOP）。

## 3. 运营风险

- **本卡是 MVP 的「演示日」**：实灌一次后，看板状态要保持「活」到演示结束。若演示前有人误操作（删数据/重置），看板就死了。建议：演示前 SOP = 跑一次完整 Run（32）→ 验证 4 条标准 → 截图存档 → 演示前不再动。
- 进度推送的实时性：若 API 通道慢（目标系统响应 1-2s/条，100 条 = 2-3 分钟），用户等待时看不到进度会以为卡死。建议：每 10 条或每 5s 更新一次进度（取先到者）。

## 4. 后续成本

- 本卡是「一次性验证」，无持续成本。
- 但「看板活」的自动化检查脚本应保留为回归工具（后续每次改动引擎/连接器后重跑），这是本卡最有价值的副产品。

## 5. 整改建议

| # | 建议 | 优先级 |
|---|------|--------|
| 1 | 定义「看板活」的 4 条量化检查项 + 自动化脚本 | 高 |
| 2 | README 里程碑明确 M3 开工门槛（Q1/Q2 落地） | 高 |
| 3 | 演示前 SOP：完整 Run → 验证 → 截图 → 不再动 | 中 |
| 4 | 进度更新频率：每 10 条或每 5s | 低 |
