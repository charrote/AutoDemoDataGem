## 一、总体结论

**方案整体通过，可以开工，但开工前必须先处理 5 个高优先级跨卡问题（R1–R5）。**

- 产品方案（01）与技术实现方案（02）方向一致、边界清晰，MVP 范围（QM-AI 双通道端到端）选得准，没有范围失控。
- 16 张任务卡的粒度（30–60min/卡）、验收标准、依赖关系总体合格；里程碑 M1→M4 的排序正确（引擎先于连接器、M3 是成败点）。
- 发现的问题分两类：**跨卡矛盾**（同一语义在两张卡里定义不一致，共 3 组）和**单卡缺口**（某卡漏了一个关键设计点，共若干）。前者必须开工前定掉，后者可在对应卡开工时补。
- 最大的未验证假设：**Q1（写 API 清单+鉴权）/ Q2（DB schema）尚未核实**，而 M3（MVP 成败点）完全依赖它们。这不是方案错误，是排期风险——建议把「Q1/Q2 核实」提升为与 M1 并行的独立工作流，而不是埋在 30 卡里等。

## 三、跨卡问题清单（开工前必须定掉）

### R1（高）｜VAULT_KEY fail-fast 与首启流程的启动顺序矛盾
- **矛盾点**：11 要求「无 `VAULT_KEY` 启动即失败」（进程级 fail-fast）；00 的验收是 `docker compose up -d` 起 api 且 `/api/health` 200；43 的模型是 web/api 先起、DB 后配。三者拼起来，用户第一次 `compose up` 必然失败（.env 还没配密钥），与「打开 8860 看到向导」的体验冲突。
- **建议决议**：`.env` 是**部署前提**（不是向导内容）：提供 `make gen-env`（一键生成 VAULT_KEY/JWT_SECRET/MYSQL_ROOT_PASSWORD），部署文档第一步就是它；fail-fast 保留（宁可报错不静默）。00 的验收改为「配好 .env 后 compose up 通」。
- **涉及卡**：00 / 11 / 43 / 44

### R2（高）｜「可复现」与「时间锚 now」的语义冲突
- **矛盾点**：20 的 seed 公式不含 now（正确），但时间锚 `anchor = now` → 同参数两次 Run，**时间戳字段必然不同**。这同时冲击 20（验收「内容完全一致」）、31（预览 vs 实灌一致性）、41（复现 = 一模一样）三张卡的验收语义。
- **建议决议**：复现语义定为「**内容确定、时间戳字段例外**」：非时间字段 100% 一致；时间戳字段 = anchor 偏移，anchor 默认 now、可显式传入（复现同一套时传同一 anchor）。写进 20 的验收标准、31 的 seed 锁定逻辑、41 的 UI 文案。
- **涉及卡**：20 / 31 / 41

### R3（高）｜Q1/Q2 未核实是 M3 的硬前置，目前埋在 30 卡里
- **风险点**：M3（30→32）是 MVP 成败点，完全依赖 Q1（写 API 清单+鉴权）和 Q2（DB schema）；而「本地有 qmai-full.sql + backend 源码」是未核实的假设（评审方无法确认其存在与新鲜度）。若 schema 与实物不符，DB 通道映射全部返工。
- **建议决议**：把「Q1/Q2 核实」从 30 卡进度里拆出来，作为**与 M1 并行的独立工作流**，验收 = ① 用 qmai-full.sql 起临时 MySQL 跑通 12 的连接测试 + schema 探测；② QM-AI 写接口逐个实测（含 compute 重算接口是否存在、流程态接口有无删除/回滚能力）。M3 开工门槛 = 这两项通过。
- **涉及卡**：30 / 32 / README 里程碑

### R4（高）｜API 通道的 manifest 退化路径 & 重置的删除能力
- **缺口**：21 的 manifest 假设「API 返回 ID 都记」，但很多写接口不返回 ID（200/204 + bool）；41 的重置假设「API 对应删除」，但流程态接口（8D/过站）往往没有 DELETE。两处不定义，21 的幂等和 41 的重置在 API 通道上都会失效。
- **建议决议**：① manifest 对 API 条目：有 ID 记 ID，无 ID 记「接口 + payload 指纹（sha256）」；② 重置语义分级：DB 通道精确删；API 通道有删除接口则删，无则标记「不可自动重置」（UI 明示，演示前人工清理）；③ R3 的 Q1 核实时必须把「哪些写接口可删/可回滚」列入实测清单。
- **涉及卡**：21 / 41 / 30

### R5（中）｜幂等检查的实现策略未定
- **缺口**：21 的「写前不重复」没定义怎么查 manifest（全量拉到内存 vs 分片 vs 阶段级断点）。大 run（数万行）下全量查询会拖慢。
- **建议决议**：推荐**阶段级断点续跑**（阶段完成才推进，失败从该阶段已完成的批之后续跑），比行级去重简单且覆盖 90% 场景；manifest 仍全量记录（服务于 41 重置）。
- **涉及卡**：21

### R6（高）｜token 生命周期策略缺失
- **缺口**：13 只写「token 缓存」，未定义存储位置、有效期来源、401 行为、并发刷新竞态。这是 API 通道（30/32 的灵魂）最易碎的点。
- **建议决议**：token 解密后内存缓存（或保险库加密存）；解析 JWT exp 判过期；调用遇 401 → 重新登录**一次** → 再失败报「认证失败」；单飞刷新（single-flight）防并发竞态。写进 13 的验收。
- **涉及卡**：13 / 21 / 30

### R7（高）｜依赖缺口：asyncpg
- **缺口**：12 的验收含 Postgres 适配，但 00 的依赖清单只有 asyncmy/aiomysql + aiosqlite。
- **建议决议**：00 依赖清单补 `asyncpg`。
- **涉及卡**：00 / 12

### R8（高）｜保险库密文缺 key_id（为密钥轮换留口）
- **缺口**：11 的密文包络无 key_id/版本字段。密钥一旦轮换，全部存量凭证不可解 → 全量重录。
- **建议决议**：密文包络加 `key_id`（当前恒为 1）。成本 ≈ 10 分钟，避免未来一周级的重录灾难。
- **涉及卡**：11

## 五、合理性 / 风险 / 成本 三维度总评

### 合理性：优
- 「按数据性质自动选路（DB/API/自算）」是产品与灌数脚本的本质差异，方案用**连接器声明式路由**（D2）实现「用户无感的自动」，而不是 ML 猜测——克制且正确，避免了过度设计。
- 值级复现（D3）+ 可选 ID 钉住，对「目标库自增 ID 不可控」这个现实约束的处理是务实的。
- 进程内异步任务（D1）、进程内插件包（D4）都是「单机 MVP 够用 + 预留升级接口」的正确取舍，没有为假想的规模上 Celery/微服务。
- MVP 只做一个连接器（QM-AI）但把「双通道都证明」作为成败点，范围收缩得准。

### 实现与运营风险：中（可控，前提是 R1–R8 落地）
- 风险集中在三处：**外部依赖**（Q1/Q2 未核实、部署机未确认）、**对目标系统的写操作**（误写/污染真实 QM-AI）、**凭证安全面扩大**（本工具持有所有目标系统账密）。
- 方案的兜底设计（Dry-Run 先行、manifest 幂等、限速、白名单、AES-GCM、租户隔离）覆盖了主要面，缺口正是本报告 R1–R8 + S4/S6 所列。
- 运营侧最容易被忽略的两点已单列：① 演示日 SOP（专用实例 / 演示前完整 Run + 截图存档）；② 目标系统把异常登录当安全事件——测试与演示环境分开。

### 后续成本：低-中（结构健康）
- 核心资产（生成引擎 / 编排器 / Registry）一次投入长期复用；扩展成本在连接器侧（每系统 1–2 人天核实 + 配置），正是「加包即扩展」的设计目的。
- 三个持续成本点要心里有数：① 连接器版本与目标系统版本绑定（QM-AI 升级 → yaml 失效）；② 保险库密钥保管 + 轮换（R8 留口后成本可控）；③ 前端 UX 迭代（「非技术用户可用」的长期打磨，预算在阶段 2）。
- 阶段 4 对外开放的安全加固（HTTPS/限流/邮箱验证）是已知成本，已在 S7 列为前置 checklist。
