> 评审人：Agent-395-Hermes ｜ 日期：2026-09-21
> 评审维度：合理性 / 实现与运营风险 / 后续成本（统一评审报告见 [README.md](./README.md)）

## 结论

**⚠️ 有条件通过** — 加密方案本身正确且克制；需补 key_id（为轮换留口）并统一「无密钥不启动」与首启向导的启动顺序（R1）。

## 1. 合理性

- AES-GCM + 每记录随机 nonce + env 单一密钥，是生产可用、复杂度最低的对称加密方案，选型正确。
- 「无密钥 → 不生效（明确报错，不 fallback）」符合严格配置原则，避免「静默明文」这种最坏情况。

## 2. 实现风险

- **与 00/43 的启动顺序矛盾（R1）**：进程级 fail-fast 意味着 .env 必须先于 `compose up` 存在。这不冲突于「web 先启动」（web 确实不依赖密钥），但部署文档必须把「先生成 .env 再起 compose」写成硬性第一步，并配生成脚本。
- **密文无 key_id/版本字段**：密钥一旦轮换，全部存量密文不可解 → 被迫全量重新录入凭证。现在在密文包络里加一个 `key_id` 字段成本几乎为零，是典型的「现在 10 分钟、将来一周」项。
- 明文「用完即弃」在异步 Python 里 GC 时机不可控；真正的风险在**异常 traceback 带出凭证**——日志脱敏需要测试覆盖（异常路径，不只是正常响应路径）。

## 3. 运营风险

- VAULT_KEY 丢失 = 所有目标系统凭证不可恢复（这是设计使然，不可恢复 ≠ 缺陷，但要让用户知道）。部署文档需写明 .env 的离线备份方式（谁持有、存哪里）。
- 目标 API token（13）也将入保险库且有过期性：401 → 重新登录的链路在 13/21 落实，此处仅提示。

## 4. 后续成本

- 密钥轮换已列 Out；**不加 key_id 则未来轮换成本极高**（全量重录）。加上后轮换 = 双写过渡，成本可控。这是本卡最重要的后续成本杠杆。

## 5. 整改建议

| # | 建议 | 优先级 |
|---|------|--------|
| 1 | 密文包络增加 `key_id`（版本字段），为轮换留口 | 高 |
| 2 | 与 00 统一口径：.env 为部署前提 + `make gen-env` 脚本 | 高 |
| 3 | 补测试：异常路径下凭证内容不出现在日志/traceback/响应中 | 中 |
