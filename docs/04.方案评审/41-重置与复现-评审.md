# 41 · 重置与复现 — 评审

> 评审对象：`docs/03.实现/41-重置与复现.md`（对应《02.技术实现方案.md》§9 任务 4.1）
> 评审人：Agent-395-Hermes ｜ 日期：2026-09-21
> 评审维度：合理性 / 实现与运营风险 / 后续成本（统一评审报告见 [README.md](./README.md)）

## 结论

**⚠️ 有条件通过** — 「只清工具灌的、不动真实数据」的安全底线正确；但 API 通道的重置能力取决于 21 的 manifest 退化路径，且「复现」与「时间锚 now」存在语义冲突（同 20）。

## 1. 合理性

- 「按 manifest ID 删除，绝不 truncate 真数据」是安全底线，设计正确。
- 值级复现（同 seed 同内容）+ ID 钉住可选，与 D3 决策一致，MVP 范围恰当。
- 「清空本系统全部工具数据」（按系统维度 manifest 汇总）覆盖「演示前一键重置为干净一套」的产品目标。

## 2. 实现风险

- **API 通道的重置是最大缺口**：DB 通道 `DELETE WHERE id IN (manifest)` 很直接；但 API 通道——**很多系统没有「删除」接口**（尤其流程态：8D 不能简单删，过站记录不能回滚）。本卡范围写「DB DELETE + API 对应删除」，但「对应删除」的前提是目标系统暴露了删除接口。若 QM-AI 的流程态接口没有 DELETE/回滚，API 通道的重置就落空。
  - 建议：Q1 核实时（30）必须确认「流程态接口是否有删除/回滚能力」；没有则重置的语义降级为「**只重置 DB 通道 + API 通道标记为不可重置（需人工清理或等系统自然过期）**」，并在 UI 明示。
- **「复现」与时间锚 now 的语义冲突**（同 20 评审）：同参数复现 → 同 seed → 但 anchor=now 不同 → 时间戳字段不同。用户预期「复现 = 一模一样」，实际时间戳变了。建议：与 20 统一——复现时可选传同一 `anchor`（复现上一套的基准时刻），或者 UI 明示「时间戳会刷新到当前」。
- **manifest 的完整性**：重置依赖 manifest 完整记录了「所有写入的 ID」。若某次 Run 中途失败（部分写入），manifest 是否记录了已写的那部分？建议：编排器（21）每写成功一批就落 manifest（而非 Run 结束才落），保证失败时 manifest 也完整。
- **「清空本系统全部工具数据」的跨 Run 汇总**：按 system_id 汇总所有 Run 的 manifest，可能涉及多个表/多个接口。删除顺序要注意外键依赖（先删从表再删主表），否则 FK 约束报错。

## 3. 运营风险

- **误操作风险**：「清空本系统全部工具数据」是危险操作（删大量数据）。建议：二次确认（输入系统名确认）+ 操作前快照 manifest（可回滚）。
- 演示场景：「演示前一键重置为干净一套」= 重置 + 重新 Run。若重新 Run 失败（目标系统慢/超时），演示前发现「看板是空的」——SOP 要预留缓冲时间（提前一天重置+Run）。

## 4. 后续成本

- 重置是低频操作（演示前），无持续维护。
- 若 API 通道无删除能力（最可能），重置的覆盖范围缩小到 DB 通道——这是已知的功能边界，不是 bug，但要让用户知道。

## 5. 整改建议

| # | 建议 | 优先级 |
|---|------|--------|
| 1 | Q1 核实时确认流程态接口的删除/回滚能力；无则重置降级为「DB 通道 + API 标记不可重置」 | 高 |
| 2 | 编排器每批落 manifest（非 Run 结束才落），保证失败时 manifest 完整 | 高 |
| 3 | 复现语义与 20 统一：可选传 anchor / UI 明示时间戳刷新 | 中 |
| 4 | 「清空全部」二次确认 + manifest 快照（可回滚） | 中 |
| 5 | 跨 Run 删除按外键依赖排序（先从表后主表） | 低 |
