# 42 · Swagger自动发现 — 评审

> 评审对象：`docs/03.实现/42-Swagger自动发现.md`（对应《02.技术实现方案.md》§9 任务 4.2）
> 评审人：Agent-395-Hermes ｜ 日期：2026-09-21
> 评审维度：合理性 / 实现与运营风险 / 后续成本（统一评审报告见 [README.md](./README.md)）

## 结论

**⚠️ 有条件通过** — 「自动发现 70% + 人工标注 30%」的定位准确；但「70%」是乐观估计，且本卡在 MVP 里的优先级建议后置（非 MVP 成败点）。

## 1. 合理性

- Swagger 自动发现把连接器最费手的「API 映射」从手写变成「自动发现 + 用户勾选」，是产品「非技术用户可配」的关键能力。
- 「自动给 70%（清单/入参/鉴权），人工标 30%（业务语义）」的定位准确——Swagger 确实给不了「哪条是流程态、调用顺序、业务取值」。
- 首次抓取存 swagger_cache（Q3 兜底：线上只 Development 开），设计正确。

## 2. 实现风险

- **「70%」是乐观估计**：实际 Swagger 的写接口解析有几个坑：
  - 请求体 schema 可能是 `$ref` 引用（$ref: '#/components/schemas/XXX'），需要递归解析，不是直接读；
  - 部分系统 Swagger 不完整（只标了路径没标 body，或 body 是 `object` 无属性）——解析失败率不低；
  - 鉴权方式：securitySchemes 可能有多种（JWT + basic + apiKey），哪个是「登录」用的，Swagger 不一定标清楚。
  建议：验收标准从「自动生成接口清单」改为「对 QM-AI 的 swagger 实测，解析成功率 ≥ X%（写接口数）」，不要承诺 70%。
- **swagger_cache 的时效性**：目标系统升级后 swagger 变了，cache 是旧的 → 解析出的接口清单过时。建议：cache 带「抓取时间」，UI 显示「缓存时间」，提供「重新抓取」按钮。
- **本卡优先级**：MVP（阶段 1）的 QM-AI 连接器（30）走「手动映射兜底」即可（产品 §6 明确「无 Swagger 退回手动」）。本卡是阶段 2「非技术用户可配」的能力，**不阻塞 MVP**。建议：从 MVP 任务列表降权到「阶段 2 前置」，MVP 只做 13 的 swagger 探测（抓得到），不做 42 的完整解析+勾选+映射。
- 解析库选型（prance vs 直接 json 遍历）：方案写「prance 或直接 json 遍历」。prance 是旧库（维护不活跃），建议直接 json 遍历（OpenAPI 是标准 JSON，解析写接口 + $ref 递归不需要重型库），避免引入维护风险。

## 3. 运营风险

- 抓 swagger 是 GET 只读，风险低。
- 若目标系统 swagger 暴露了敏感接口（admin/内部接口），「可配置接口清单」里会列出——用户勾选时可能误选危险接口。建议：UI 对 DELETE 接口加黄色警告（「删除类接口，谨慎勾选」）。

## 4. 后续成本

- 中。本卡是「新系统接入的加速器」——每接入一个新系统都受益。但「70%」若达不到，收益打折。
- 解析逻辑一次投入，后续维护低（OpenAPI 标准稳定）。

## 5. 整改建议

| # | 建议 | 优先级 |
|---|------|--------|
| 1 | MVP 降权：只做 13 的 swagger 探测，42 的解析+勾选+映射归阶段 2 | 高 |
| 2 | 解析库用 json 遍历（不引入 prance） | 中 |
| 3 | 验收改为「QM-AI swagger 实测解析成功率」，不承诺 70% | 中 |
| 4 | swagger_cache 带抓取时间 + 「重新抓取」按钮 | 低 |
| 5 | DELETE 类接口 UI 加警告 | 低 |
