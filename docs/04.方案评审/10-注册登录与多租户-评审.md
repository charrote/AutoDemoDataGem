# 10 · 注册登录与多租户 — 评审

> 评审对象：`docs/03.实现/10-注册登录与多租户.md`（对应《02.技术实现方案.md》§9 任务 1.0）
> 评审人：Agent-395-Hermes ｜ 日期：2026-09-21
> 评审维度：合理性 / 实现与运营风险 / 后续成本（统一评审报告见 [README.md](./README.md)）

## 结论

**✅ 通过** — 多租户模型对 MVP 恰当；验收标准需补「跨租户」的具体测试面。

## 1. 合理性

- 注册即建租户、一人一租户，砍掉团队概念，MVP 范围恰当。
- JWT 携带 `tid` + repository 层强制 `tenant_id` 作用域，是多租户隔离的标准做法。

## 2. 实现风险

- 「基类注入杜绝裸表查询」是 Python 层面的约定，不是强制。建议验收标准把「跨租户查询一律 403」落到**具体接口矩阵**：注册 A/B 两用户，A 对 B 的 systems / runs / manifest 的读与写各返回 403——现在只有一句话，测试时容易漏面。
- `users.username` 未声明唯一约束（一人一租户下应全局唯一），不补则注册可重名。
- passlib 处于维护模式（bcrypt 弃用告警），建议直接锁定版本或评估换用 `bcrypt` 库直调。

## 3. 运营风险

- 开放注册 + 无审批：MVP 内部使用可接受，但阶段 4 对外开放后是真实攻击面（批量注册/撞库）——与 44 的 TLS/限流联动，见统一报告 R9。
- JWT 存 localStorage（方案 §6）：XSS 即泄漏。MVP 单用户场景可接受，需在方案中显式记录该取舍。

## 4. 后续成本

低。tenant 作用域是一次性纪律，后续所有模块复用，边际成本低。

## 5. 整改建议

| # | 建议 | 优先级 |
|---|------|--------|
| 1 | 补 `username` 全局唯一约束 | 中 |
| 2 | 验收补跨租户集成测试矩阵（A/B 两租户 × systems/runs/manifest × 读写） | 高 |
| 3 | 记录 JWT 存储取舍（localStorage vs httpOnly cookie），阶段 4 前重评 | 低 |
