# 12 · 系统CRUD与DB连接测试 — 评审

> 评审对象：`docs/03.实现/12-系统CRUD与DB连接测试.md`（对应《02.技术实现方案.md》§9 任务 1.2）
> 评审人：Agent-395-Hermes ｜ 日期：2026-09-21
> 评审维度：合理性 / 实现与运营风险 / 后续成本（统一评审报告见 [README.md](./README.md)）

## 结论

**⚠️ 有条件通过** — 设计合理；PG 驱动缺失（联动 00）与 schema_cache 无上限需要处理。

## 1. 合理性

- DBDriver 抽象（mysql/sqlite/postgres）+ 全参数化 SQL 是对「目标库千差万别」的正确应对。
- 连接测试 = 建连 → 探 schema → 抽样 → 健康报告，且要求报错区分网络/认证/库不存在，对非技术用户友好，验收标准质量高。
- schema 探测结果缓存到 `systems.schema_cache`，供连接器做字段映射与 dry-run，数据流正确。

## 2. 实现风险

- **依赖缺口（R7）**：Postgres 驱动 `asyncpg` 不在 00 的依赖清单里，本卡验收却含 PG 适配。
- **schema_cache 无大小上限**：大 schema（数百表 × 列）会让 systems 单行 JSON 膨胀，拖慢所有 systems 查询。建议：只探测连接器 manifest 声明的表（白名单）+ 列数上限，探测结果带时间戳。
- 连接测试必须**严格只读**：SELECT only，驱动支持时显式开只读事务，防止「探一下」对目标库产生副作用。
- 目标库可能是受限账号（无 SELECT 部分表/无 SHOW 权限）：权限类错误要归入健康报告的错误分类，不能当「连接失败」处理。

## 3. 运营风险

- 低。测试是只读探测，风险主要在第 2 节已列的「非只读」实现失误。

## 4. 后续成本

低。驱动层一次性；新增目标库类型 = 加一个 driver（频率低）。

## 5. 整改建议

| # | 建议 | 优先级 |
|---|------|--------|
| 1 | 依赖清单补 `asyncpg`（与 00 联动） | 高 |
| 2 | schema 探测加范围控制：连接器 manifest 表白名单 + 列数上限 + 时间戳 | 中 |
| 3 | 连接测试强制只读（SELECT only / 只读事务） | 中 |
