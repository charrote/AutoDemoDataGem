## 结论

**✅ 通过** — 设计合理，是防误写的前置闸门；一处实现细节建议补齐（预览样本与真实 Run 的一致性）。

## 1. 合理性

- Dry-Run 先行是方案 §10 风险表的第一条兜底，本卡是它的 UI 落地。
- 样本 + ECharts 预览（趋势/分布/状态占比）+ 预估写入量，直接服务「非技术用户确认后再真写」的产品目标。
- 「4 条标准自检：预览即验证看起来活」——把验收标准前置到预览环节，设计巧妙。

## 2. 实现风险

- **预览样本与真实 Run 的数据一致性**：预览取「生成引擎产物的一段」，真实 Run 重新生成。若预览时用了不同的 seed 或 anchor（now），用户看到的样本和实际灌入的数据会不一致 → 用户信任崩塌。建议：预览与真实 Run 用**同一 seed**（seed 在用户点「预览」时锁定，存到 runs.params，确认运行后复用），保证「预览所见 = 实际所得」。
- 预估写入量「按表/按接口」：若生成引擎是分块产出的，预估需要先生成完整 plan（内存峰值）。大 run（10 万行）的预览会慢。建议：预估基于场景配方的 count 参数直接算（不实际生成），生成引擎只产出一段样本（如 100 行）用于图表。
- ECharts 预览图（趋势/分布/饼）是前端渲染，本卡范围是「后端出数据」还是「前端画图」未明。建议明确：本卡 = 后端出预览数据 API（样本 + 统计量），前端画图归 40。

## 3. 运营风险

低。Dry-Run 不碰目标系统，纯计算。

## 4. 后续成本

低。预览是一次性功能，无持续维护。

## 5. 整改建议

| # | 建议 | 优先级 |
|---|------|--------|
| 1 | 预览与真实 Run 锁定同一 seed（预览时生成 seed 存 runs.params） | 高 |
| 2 | 预估写入量基于 count 参数直接算，不实际生成全量 | 中 |
| 3 | 明确边界：本卡 = 后端预览 API，前端画图归 40 | 低 |
