# 40 · 前端控制台 — 评审

> 评审对象：`docs/03.实现/40-前端控制台.md`（对应《02.技术实现方案.md》§9 任务 4.0）
> 评审人：Agent-395-Hermes ｜ 日期：2026-09-21
> 评审维度：合理性 / 实现与运营风险 / 后续成本（统一评审报告见 [README.md](./README.md)）

## 结论

**⚠️ 有条件通过** — 页面清单与非技术用户定位一致；两处需明确：与 42/43 的页面边界，以及「实时日志流」的技术选型。

## 1. 合理性

- 页面清单（系统接入 / 场景+参数 / Dry-Run 预览 / 运行+监控 / 重置入口）与产品核心功能 1:1 对应，无多余页面。
- 「滑块 + 数值」调参、连接测试实时回显，符合「非技术用户一等公民」。
- UI 规范（禁 emoji、SVG 图标、Tab 激活色 #3B82F6、状态卡不用左彩色竖条）具体可执行，不是空话。

## 2. 实现风险

- **页面边界与 42/43 重叠**：本卡 Out 里排除了首启向导（43）和 Swagger 发现（42），但「系统列表 / 新建系统」页与 43 的向导页在「未初始化」状态下是同一个入口。需要明确：`initialized=false` 时整站只有向导（43），`true` 后才渲染本卡的系统列表——两者靠 `/api/status` 切换，不是两套独立入口。建议在卡片里写明这个状态机归属（43 管切换，40 管切换后的控制台）。
- **实时日志流技术选型未定**：「WebSocket/轮询」二选一。建议 MVP 统一用**轮询**（与 21 的建议一致）：实现简单、nginx 反代无 WS 配置、断线自动恢复。WebSocket 留阶段 2。
- **失败定位「哪条接口哪条数据」的前端展示**：后端日志是文本流，前端要把「失败定位」做成可点击定位（点击日志行 → 高亮对应数据），不是纯文本滚动。这是一个容易被忽略的交互设计点。
- 31 的预览图（ECharts 趋势/分布/饼）在本卡的「Dry-Run 预览页」渲染——本卡与 31 的边界是「31 出数据 API，40 画图」，与 31 评审建议一致。

## 3. 运营风险

- 低。纯前端，无外部系统操作。
- JWT 存 localStorage（方案 §6）：XSS 风险（10 已评）。

## 4. 后续成本

- 前端是持续成本最高的部分（UI 打磨、交互迭代）。MVP 基础版够用，但「非技术用户可用」的标准意味着后续会有大量 UX 反馈——建议预留阶段 2 的「可视化增强」预算。
- ECharts + Element Plus 的 bundle 体积大，首屏加载慢。建议代码分割（按页面懒加载）。

## 5. 整改建议

| # | 建议 | 优先级 |
|---|------|--------|
| 1 | 明确与 43 的状态机边界：/api/status 切换，43 管未初始化、40 管已初始化 | 中 |
| 2 | MVP 统一用轮询（不用 WebSocket），与 21 一致 | 中 |
| 3 | 失败定位做成可点击交互（日志行 → 数据高亮） | 低 |
| 4 | 按页面懒加载（代码分割），控制首屏体积 | 低 |
