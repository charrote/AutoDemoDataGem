## 结论

**⚠️ 有条件通过** — 可插拔登录策略合理；token 缓存的过期/失效策略必须补（R6），否则 API 通道在 21/30/32 会反复踩坑。

## 1. 合理性

- ApiClient + 可插拔登录策略（JWT / basic / header token）是适配多系统鉴权的正确抽象，QM-AI 的 JWT Bearer 只是第一个实例。
- swagger 探测路径可配（`/swagger/v1/swagger.json` 或 `/openapi.json`），覆盖 Q3（线上只 Development 开）的变体。

## 2. 实现风险

- **token 缓存策略缺失（R6）**：卡片只写「token 缓存」，未定义：
  - 存哪（保险库加密存？内存？）、有效期从哪来（JWT 解析 exp vs 目标系统实际失效）；
  - 401/403 时的行为：重新登录 vs 直接失败。建议：解密缓存 token → 调用 → 401 → 重新登录一次 → 再失败才报「认证失败」；
  - 并发调用共享同一 token 的刷新竞态（单飞刷新，single-flight）。
  这是 API 通道最易碎的点，30/32 直接依赖它。
- 「登录失败 / 无 swagger 分别清晰提示」很好，但**登录接口本身也可能被目标系统限流**（连续测试触发风控）：测试动作要带退避。
- 目标系统登录可能有验证码/2FA/图形码——可插拔策略应预留「人工介入」钩子（MVP 可不做，但要意识到这是真实系统的常态，验收里 QM-AI 先跑通即可）。

## 3. 运营风险

- 探测 swagger 是 GET 只读，风险低；但「自动登录」意味着本工具持有目标系统真实账号密码，凭证保管面扩大（与 11 联动）。
- 若目标系统把异常登录当安全事件报警（生产 QM-AI 有日志），演示前反复测试会留下痕迹——运营上建议：正式演示环境与测试环境分开，或测试后清理登录日志。

## 4. 后续成本

低。登录策略新增 = 加一个 strategy 类（频率低）。

## 5. 整改建议

| # | 建议 | 优先级 |
|---|------|--------|
| 1 | 补 token 生命周期策略：缓存位置（加密）/ exp 解析 / 401 单次重登 / 单飞刷新 | 高 |
| 2 | 探测动作带退避，避免触发目标系统风控 | 中 |
| 3 | 登录策略预留「人工介入」钩子（文档级，MVP 不实现） | 低 |
