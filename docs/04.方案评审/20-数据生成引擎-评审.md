> 评审维度：合理性 / 实现与运营风险 / 后续成本（统一评审报告见 [README.md](./README.md)）

## 结论

**⚠️ 有条件通过** — 引擎设计是产品灵魂，方向完全正确；两个实现细节会直接破坏「可复现」承诺（seed 混入 now + Faker 版本漂移），必须在实现前钉死。

## 1. 合理性

- seed 派生（sha256(tenant|system|scene|canonical(params))）+ 所有随机量只从 rng/faker 取，是「同参数→同内容」的正确实现路径。
- 时间锚 now + 近 24h 密集「实时尾巴」，直接服务「时间新鲜」标准，设计巧妙。
- DAG 拓扑序生成 + 外键引用真实主 ID，解决「从表指向不存在工单」的露馅点。
- 声明式 Generator 规格（categorical/normal/poisson + anomaly_rate）把「分布合理 + 有异常」变成配置，而非硬编码，扩展性正确。

## 2. 实现风险

- **seed 混入 now 会破坏复现（R8 的一部分）**：方案 §4.1 的 seed 公式不含 now，是对的；但 §4.2 的时间锚 `anchor = now` 意味着**同 seed 两次生成，时间戳不同** → 违反 2.0 验收「同参数两次生成内容完全一致」。必须明确：复现基准是**内容（非时间戳字段）确定**，时间戳字段允许偏移一个运行时刻；或者把 anchor 也纳入 params（用户显式传「基准时刻」）。建议：默认 anchor=now（保证「看起来新鲜」），文档与验收明确「时间戳字段除外」的复现语义，并提供可选 `anchor` 参数（复现同一套时传同一时刻）。
- **Faker 版本漂移**：Faker 的 zh_CN 数据池随版本变化，同 seed 跨版本生成内容不同。Docker 镜像必须锁 Faker 精确版本（requirements 锁 `==`），否则「可复现」在升级后静默失效。
- numpy `default_rng` 的 API 稳定，风险低；但**生成顺序必须确定性**——DAG 拓扑序遇到同层多节点时，顺序要按声明顺序排序，不能依赖 dict/set 的哈希序（Python 3.7+ dict 保序 OK，set 不行）。
- canonical(params) 的「键排序 + 稳定序列化」要覆盖嵌套 dict/列表，建议直接 `json.dumps(sort_keys=True, ensure_ascii=False)` 并单测覆盖嵌套结构。

## 3. 运营风险

- 低。引擎是纯计算，不碰外部系统。
- 唯一运营点：「实时尾巴」让数据永远以 now 为锚 → 每次重新 Run 都会刷新时间，这与「可复现」在语义上轻微冲突（用户预期「复现 = 一模一样」，实际时间戳不同）。需在 UI/文档明示，避免用户误以为 bug。

## 4. 后续成本

- 引擎本身是核心资产，一次投入长期复用。
- 新分布类型（如 lognormal、seasonal）= 加一个 Generator 规格解析器，成本中等、频率低。
- **版本漂移的复现失效是持续成本**：不锁版本，每次依赖升级都是潜在 bug。锁版本后成本归零。

## 5. 整改建议

| # | 建议 | 优先级 |
|---|------|--------|
| 1 | 明确复现语义：时间戳字段除外（或 anchor 可传入）；写进验收标准与 UI 文案 | 高 |
| 2 | Docker 镜像锁 Faker 精确版本（`faker==x.y.z`），写进 00 依赖清单 | 高 |
| 3 | DAG 同层节点按声明序排序，保证生成顺序确定 | 中 |
| 4 | canonical(params) 用 `json.dumps(sort_keys=True)`，补嵌套结构单测 | 中 |
