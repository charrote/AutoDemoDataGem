# AutoDemoDataGem — 产品方案

> **定位**：一个「让 Demo 系统看起来真的在跑业务」的自动灌数工具（SaaS）。
> 用户在服务器注册后，接入自己的 Demo 系统，一键灌入真实感的数据——演示时「功能全 + 数据活」。

---

## 一、解决什么问题

- Demo 系统（MES / QM / EM…）功能全，但**数据是空的**。
- 给人演示时：列表空、看板没数、实时状态没有，很尴尬。
- 现状：手写 SQL 灌数——慢、易错、不真实，每次演示都要重来。
- **产品目标：一键、可配、看起来真的在跑，非技术的人也能配。**

## 二、用户是谁

- 有 Demo 系统要演示的**厂商 / 集成商**。
- 系统功能全但数据空，想要「丰满、真实」的演示数据。
- 不想自己写 SQL，要**可视化、可复现**。

## 三、核心功能（用户视角）

1. **注册 / 登录**（开放注册，注册即用）。
2. **接入 Demo 系统**：填 DB 连接 / API 地址 / 凭证。
3. **选场景**：要灌什么（质量检验 / 设备维护 / 生产工单…）。
4. **调参数**：多少天 / 多少条 / 多少异常。
5. **一键灌入** → 看效果。
6. **可复现 / 重置**：同一参数复现同一套；演示前一键重置为干净一套。

## 四、数据「看起来活」的标准

| 标准 | 说明 | 反例（露馅） |
|------|------|------------|
| **时间新鲜** | 以当前时间为锚，趋势图 / 实时有数据 | 数据是去年的 |
| **有关系** | 从表引用的主表真实存在 | 检验记录指向不存在的工单 |
| **分布合理** | 数值在规格内、状态按真实比例分布 | 100% 合格、数值全在正中 |
| **有异常** | 看板有红点、有故事可讲 | 全绿、无戏可讲 |

## 五、一个关键技术点（为什么不是简单 INSERT）

不是所有数据都能直接插库，工具要**按数据性质自动选路**：

| 数据 | 例子 | 怎么灌 | 为什么 |
|------|------|--------|--------|
| **扁平记录** | 检验记录、日志、主数据 | 直接写库 | 快，「看得到」即可 |
| **流程 / 状态** | 工单过站、设备状态流转 | 走系统 API 推进 | 直接插库 = 「假死」，一操作就露馅 |
| **看板 / 汇总** | 不良率、SPC、KPI | 系统自己算 | 触发重算即可，不用手写 |

> **用户永远不用管走哪条路，工具自动判断。** 这是「产品」和「灌数脚本」的区别。

## 六、产品形态

- **一个 SaaS**：服务器部署，注册即用，多租户隔离（每个用户管自己的 Demo 系统）。
- **系统连接器**：每支持一个 Demo 系统，写一个「连接器」（这个系统的表结构 + API 映射 + 场景配方）。**支持新系统 = 加一个连接器**，不是一次性活。
- **控制台**：可视化配置（接系统 / 选场景 / 调参 / 预览 / 一键运行 / 监控）。

### 支持范围（本阶段门槛）

一个 Demo 系统**至少要具备数据库或 API 中任意一种**，才能被本产品支持：
- 有 DB → 扁平记录走 DB 灌入。
- 有 API → 流程 / 状态型走 API 推进。
- **两者都没有**（纯前端 / 无后端数据层）→ **本阶段不在考虑范围**，不为其做连接器。

### 接入系统：Swagger 自动发现（可配置接口）

系统提供 **Swagger / OpenAPI** 时，工具可**自动发现"可配置接口"**，把连接器里最费手的 API 映射从手写变成"自动发现 + 用户勾选"：

```
填 base URL + 凭证
  → 工具自动登录拿 token
  → 拉取 swagger.json（/openapi.json）
  → 解析所有写接口（POST/PUT/PATCH/DELETE）+ 请求体 schema
  → 控制台列出"可配置接口"，用户勾选 + 映射字段
  → 场景配方引用这些接口
```

- **Swagger 自动给**：接口清单、入参字段/类型、鉴权方式 → 可配置接口列表自动生成（占连接器 API 部分约 70%）。
- **Swagger 给不到（仍需连接器人工标注）**：哪条是流程/状态型、调用顺序（依赖）、业务合理取值、派生重算触发点、写后状态自洽验证。
- **无 Swagger 的系统**：退回手动配 API 映射（连接器声明）。

> QM-AI 实测：Swagger 有（`/swagger/v1/swagger.json`）、鉴权 = JWT Bearer（登录 `POST /api/auth/login`）、38 个 Controller。⚠️ Swagger 仅 Development 环境开启，线上 Demo 需确认开启或首次抓取存一份。

## 七、MVP 范围

- 注册 / 登录 + 多租户（每用户管自己的系统，凭证加密、仅本用户可用）。
- 接入系统（DB + API）。
- **QM-AI 连接器端到端跑通**：接系统 → 选场景 → 调参 → 灌入 → 看效果。
- **双通道（DB + API）都支持**——流程型数据走 API 是产品的灵魂，必须证明。QM-AI 质量检验全链路：主数据 / 历史检验记录走 DB，活跃 / SPC / 8D 等流程态走 API。
- 数据「看起来活」的 4 条标准达成。
- 可视化控制台（基础版）。

## 八、技术栈

- **后端**：Python/FastAPI（写库、调 API、生成数据生态最全；与目标系统栈解耦）。
- **前端**：简洁表单（非技术用户一等公民）。
- **凭证**：目标系统 DB 连接串 / API 凭证加密存储，仅本用户可用。
- **部署**：Docker Compose 单机（服务器 `uantek@nat.ywapi.com`，是否同机待确认）。

## 九、路线图

| 阶段 | 内容 | 交付物 |
|------|------|--------|
| **1** | 注册/登录 + 接入系统 + **QM-AI 连接器**跑通（DB + API 双通道） | 最小可演示闭环 |
| **2** | 可视化控制台 + 数据「活」的 4 条标准 | 非技术用户可用 |
| **3** | 第 2、3 个连接器（EM-AI 实时、MES Lot 流程） | 平台扩展点验证 |
| **4** | 开放注册上线 + 服务器部署 | 对外可用 |

## 十、待确认

1. **QM-AI 的写 API 清单 + 鉴权**（JWT/Token/登录态）——流程型走 API 的前提。按"可用"处理，但**实现第一步先核实一遍**（哪些写接口、鉴权方式），确认 API 通道能落地。
2. **QM-AI 的 DB schema**：需要灌哪些表、外键关系、字段语义（决定 DB 通道的映射）。
3. **凭证加密方案**（设计阶段定）。
